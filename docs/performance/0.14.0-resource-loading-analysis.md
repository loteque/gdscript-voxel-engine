# 0.14.0 Resource-Loading Analysis

## Purpose

Measure the existing single-LOD runtime streaming path under controlled loading concurrency before making further loading or LOD architecture decisions.

The automated experiment answers a narrow native-headless question:

> How do throughput, per-load latency, residency completion cost, and asset-complexity correlation change as `ChunkStreamer.max_concurrent_loads` varies while the production dataset, residency policy, scheduling budget, and traversal remain fixed?

Browser and rendered-native observations remain separate follow-up evidence because headless execution cannot establish GPU draw cost or mobile-Web scheduling behavior.

## Dataset and configuration

The experiment uses the same deterministic production fixture as `ChunkStreamingValidationDemo`:

- 169 precomputed single-LOD chunks (`13 x 1 x 13` region)
- chunk cell dimensions: `12 x 12 x 12`
- sample spacing: `1.0`
- LOD: `0`
- load radius: `2`
- unload radius: `3`
- load-start budget: `2` per process update
- tested maximum concurrent loads: `1`, `2`, `4`, `8`
- 11 deterministic chunk-space waypoints spanning the fixture

Each waypoint is converted to a chunk-center terrain position and passed through `ChunkStreamer.update_residency()`. The experiment waits for pending work to settle before advancing to the next waypoint. This deliberately exercises the normal residency, scheduler, threaded `ResourceLoader`, and resident `MeshInstance3D` creation paths without invoking procedural generation.

The fixed waypoint traversal is an analysis workload, not a simulation of the demo target's exact real-time movement speed. It is intended to compare loading configurations under identical residency transitions.

## Measured evidence

### Concurrency matrix

| Maximum concurrent loads | Median sweep duration | Mean load latency | Mean background wait | Mean residency completion | Peak active loading | Completed loads | Unloads |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1416.98 ms | 6.73 ms | 6.71 ms | 0.020 ms | 1 | 183 | 153 |
| 2 | 796.04 ms | 6.66 ms | 6.64 ms | 0.022 ms | 2 | 183 | 153 |
| 4 | 720.22 ms | 6.50 ms | 6.48 ms | 0.020 ms | 4 | 183 | 153 |
| 8 | 713.27 ms | 6.56 ms | 6.55 ms | 0.016 ms | 6 | 183 | 153 |

All three repetitions at every concurrency level completed exactly 183 loads and 153 unloads. Peak resident count was 33 and peak queued count was 25 in every case.

The maximum observed loading count at configured concurrency 8 was 6 rather than 8. This is an observation of this workload with a two-start-per-update budget and fast native-headless completions, not evidence that `ChunkStreamer` cannot reach eight active requests under a different workload.

### Relative sweep-duration changes

Using median sweep duration:

- concurrency `1 → 2`: approximately **43.8% shorter**
- concurrency `2 → 4`: approximately **9.5% shorter**
- concurrency `4 → 8`: approximately **1.0% shorter**

### Per-load observations

Across 549 load observations per concurrency group:

- median aggregate load latency was 7 ms for every concurrency level;
- p95 aggregate load latency was 7 ms for every concurrency level;
- mean aggregate latency remained in the narrow 6.50–6.73 ms range;
- mean background wait remained in the narrow 6.48–6.71 ms range;
- mean residency completion remained approximately 0.016–0.022 ms;
- most residency-completion samples were 0 ms at the millisecond-resolution observation boundary.

`ChunkStreamer` records completion through process polling, so these timings are polling-cadence observations rather than profiler-precise worker completion timestamps.

### Asset-size and mesh-complexity correlation

Pearson correlation between baked asset characteristics and aggregate latency was close to zero in every concurrency group:

| Concurrent loads | Serialized bytes vs aggregate latency | Vertex count vs aggregate latency | Index count vs aggregate latency |
| ---: | ---: | ---: | ---: |
| 1 | -0.028 | -0.033 | -0.026 |
| 2 | -0.013 | -0.016 | -0.014 |
| 4 | -0.063 | -0.058 | -0.073 |
| 8 | -0.068 | -0.070 | -0.068 |

Within this fixture's asset-size/complexity range, the native-headless experiment did not observe a positive relationship between larger/more complex chunks and load latency.

This does not establish that asset size is irrelevant at substantially larger chunk sizes or on Web. It only describes the tested fixture and environment.

### Headless process cadence

Peak measured process gaps were roughly 15.7–18.4 ms across the cases. These values include CI scheduling and headless engine cadence and **must not be reported as rendered frame times**.

## Engineering inference

The native-headless data suggests the current loading pipeline reaches most of its useful throughput improvement by concurrency 4 for this fixture and runner. Increasing the configured maximum from 4 to 8 produced almost no additional sweep-throughput improvement.

Because average per-load latency remained essentially flat as concurrency increased, the throughput improvement from 1 to 4 is consistent with overlapping independent asynchronous resource loads rather than making each individual load faster.

The extremely small observed residency-completion component indicates that, in native-headless CI, creating and installing the normal resident `MeshInstance3D` is not the dominant measured cost. Nearly all observed aggregate latency lies before that boundary, in the asynchronous/background-loading interval.

The near-zero asset-characteristic correlations suggest that variation among the current baked chunks is not large enough to explain native-headless load-latency variation. This weakens, but does not eliminate, the hypothesis that smaller LOD assets alone would solve the previously observed mobile-Web multi-second loading latency.

The large gap between these native-headless measurements (approximately 6.5 ms average per load) and prior mobile-Web validation observations measured in seconds strongly suggests that the material scaling problem is platform/browser-specific or otherwise absent from native-headless execution. The headless experiment therefore cannot replace Web measurements.

## Decisions

1. Keep the automated headless experiment as a reproducible regression/evidence tool. Do not use performance thresholds as CI pass/fail criteria.
2. Treat concurrency 4 as the useful native-headless comparison point for the current fixture unless browser evidence shows materially different behavior.
3. Do not raise default concurrency solely because the native-headless runner can tolerate it; concurrency 8 showed negligible additional throughput here.
4. Do not implement LOD or restructure `ChunkStreamer` based on this headless run alone.
5. Preserve browser/manual measurements as the next required evidence because the previously observed problem is not reproduced by native-headless loading.

## Rendering limitation

The experiment intentionally does **not** pretend to simulate rendered performance.

Headless Godot still exercises:

```text
TerrainChunkManifest
    ↓
ChunkStreamer
    ↓
threaded ResourceLoader
    ↓
TerrainChunkAsset
    ↓
MeshInstance3D creation / residency ownership
```

It does not provide representative GPU submission, rasterization, browser compositor behavior, mobile GPU cost, or rendered Web frame time. Adding artificial CPU work to mimic rendering would create a synthetic alternate workload and would not improve the validity of the resource-loading measurement.

If rendered cost becomes the next question, use a real rendered native/Web experiment with the same traversal and configuration rather than modifying the headless loader workload.

## Open questions and next experiments

1. Run the same controlled concurrency values (`1`, `2`, `4`, `8`) in the published desktop-Web and mobile-Web Integration Preview.
2. Record Web cache provenance for every accepted run (`first-load / cold-ish`, `repeated / warm`, or `unknown`).
3. Compare Web background-wait and residency-completion timing against the native-headless baseline.
4. Determine whether mobile-Web throughput also saturates around concurrency 4 or whether browser scheduling/network/resource behavior changes the optimum.
5. Compare first-load and repeated-load Web runs to estimate how much of the multi-second behavior is cache-sensitive.
6. If Web latency remains asset-dependent, expand the asset-size/mesh-complexity range before inferring an LOD benefit.
7. Use a real rendered experiment if frame-time/GPU cost becomes material; do not infer it from the headless process-gap metric.
