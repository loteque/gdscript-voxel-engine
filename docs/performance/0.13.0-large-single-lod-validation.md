# 0.13.0 Large Single-LOD Streaming Validation

## Purpose

This report records the first materially larger runtime-streaming validation of the precomputed terrain pipeline introduced through PR #48.

The experiment was intended to answer:

> How does the first-generation single-LOD streaming architecture behave when the amount of precomputed terrain becomes meaningfully larger than the original validation fixture?

The goal was not to benchmark the final several-kilometer asteroid or justify LOD in advance. It was to establish a reproducible scaling baseline and identify the first constraints visible under larger runtime load.

## Architecture under test

The dataset was generated offline through the production path:

```text
PointFieldResource
    ↓
SurfaceNetsMesher
    ↓
ArrayMesh
    ↓
ChunkAssetBaker
    ↓
TerrainChunkAsset
    ↓
TerrainChunkManifest
```

Runtime used only precomputed assets:

```text
TerrainChunkManifest
    ↓
ChunkStreamer
    ├── load / unload residency radii
    ├── nearest-first queue ordering
    ├── per-frame load-start budget
    ├── maximum concurrent loads
    ├── threaded ResourceLoader execution
    └── resident MeshInstance3D instances
```

No runtime point-field generation, Surface Nets meshing, procedural fallback, or LOD was used.

The 169-chunk fixture is 6.76 times the chunk count of the previous 25-chunk streaming fixture while retaining the same chunk resolution.

The automated traversal was later changed to wait whenever residency work was pending. This validation-only backpressure prevents the moving target from outrunning the loader and allows the scale test to distinguish loading throughput from spatial-residency correctness.

## Automated validation evidence

The deterministic large streaming test established that:

- the baked manifest contains exactly 169 expected entries;
- all generated chunk assets deserialize as valid single-LOD `TerrainChunkAsset` resources;
- a radius-two admission region creates 25 candidate chunks in the interior of the dataset;
- nearest-first scheduling still prioritizes the target chunk;
- the two-start-per-frame budget remains respected;
- the four-concurrent-load limit remains respected;
- the initial residency region settles correctly;
- movement exercises hysteretic retention and later eviction;
- peak residency, completion, failure, unload, and cancellation metrics update coherently;
- metrics snapshots and reset operations do not mutate residency state; and
- runtime streaming remains independent of `PointFieldResource`, `SurfaceNetsMesher`, and procedural runtime meshing.

The published Integration Preview was also manually verified with visible terrain around the target and functioning Web worker diagnostics.

## Engineering inference

The following conclusions are interpretations of the measured evidence rather than direct measurements.

### Loading throughput is the first material scaling constraint

During active loading, all four concurrent slots were occupied while queued work remained. This indicates that the scheduler was feeding the loader and that the four-request concurrency ceiling was saturated rather than starved.

Using the accepted mobile-Web average latency as a rough throughput estimate:

```text
4 concurrent requests / 2.22 seconds ≈ 1.8 chunk completions per second
```

This is only an order-of-magnitude estimate. Individual threaded resource requests overlap, and the instrumentation does not yet decompose fetch, resource deserialization, mesh reconstruction, and instance creation into separate timings.

The observation nevertheless suggests that resource-loading throughput, rather than queue ordering, is the first obvious runtime scaling pressure on this mobile-Web configuration.

### Residency and hysteresis remain correct

Once the target stops outrunning the loader, the residency region converges around the correct target position and pending cancellations fall from 98 to zero. This strongly indicates that the earlier spatially intermittent terrain was caused by validation traversal outrunning available loading throughput, not by incorrect chunk-coordinate conversion or hysteresis semantics.

### No meaningful mesh-memory pressure is visible yet

The accepted run reported approximately 0.39 MiB of resident mesh memory at 32 resident chunks, with a peak residency of 36 chunks.

This metric is intentionally approximate and does not represent complete process, renderer, resource-cache, WebAssembly, or GPU memory use. It is sufficient only to say that the current mesh estimate does not identify memory as the first scaling bottleneck.

### Main-thread frame collapse was not observed

The observed mobile-Web frame time stayed around 31–33 ms with recent maxima in the mid-to-high 30 ms range during the captured runs.

These are validation-scene observations rather than controlled frame-time benchmarks. They do not isolate streaming cost from device/browser rendering cost. They do, however, show no evidence in this experiment of multi-second load latency translating directly into equivalently severe frame stalls.

## Decisions

Based on this milestone:

1. Keep the current offline/runtime contract intact. The data does not justify runtime procedural generation as a fallback.
2. Do not introduce LOD merely because the first large dataset loads slowly. First investigate where threaded resource-loading time is spent.
3. Do not add memory-budget or eviction sophistication based on this run; no material resident-mesh-memory pressure was observed.
4. Do not increase concurrency or enable more aggressive loader behavior inside the 0.13.0 validation milestone. Preserve this result as a baseline for controlled follow-up experiments.
5. Keep validation traversal backpressure in the large streaming demo so human QA can observe correct eventual residency independently of device-specific loading throughput.
6. Do not split `ChunkStreamer` solely because metrics were added. The scale result did not show an ownership or maintainability failure that requires an immediate scheduler/residency extraction.

## Open questions and next experiments

The primary unresolved question is what comprises the approximately 2.2-second average mobile-Web load latency.

Useful follow-up experiments include:

- separating threaded request duration from post-load `MeshInstance3D` creation time;
- comparing native desktop, desktop Web, and mobile Web load latency for the same baked assets;
- testing controlled `max_concurrent_loads` values against throughput and frame-time impact;
- determining whether resource size, Godot resource deserialization, Web filesystem/cache behavior, or mesh reconstruction dominates individual chunk latency;
- measuring complete process/GPU memory with more appropriate tooling before making memory-policy decisions; and
- using those results, rather than intuition alone, to decide what problem LOD should solve.

## Architectural implication

The 0.13.0 evidence does not yet justify a broad `ChunkStreamer` refactor.

Residency policy, scheduling, load execution, runtime instance ownership, and lightweight observability remain distinguishable internal stages. A later LOD design may create enough policy pressure to justify extracting a `ChunkResidencyPolicy`, `ChunkLoadScheduler`, or another subsystem, but that decision should be based on the requirements and measurements of that later milestone.

## Baseline summary

The first-generation runtime stack successfully streamed a 169-chunk deterministic single-LOD dataset through the production offline/runtime boundary. Correct residency, nearest-first scheduling, bounded async loading, hysteresis, and eventual visible geometry were all validated.

The first material scaling constraint observed on Firefox for Android is slow precomputed-resource loading, with approximately 2.2 seconds average measured load latency under a four-concurrent-load configuration. The experiment did not identify mesh-memory pressure or a residency-policy correctness failure as the immediate bottleneck.
