# Web Resource-Loading Microbenchmark

## Purpose

The rendered mobile-Web streaming matrix established a platform-specific loading pattern that the native headless experiment does not reproduce: increasing `ChunkStreamer` concurrency raises observed request latency without materially improving traversal throughput, while residency completion remains cheap.

This experiment narrows the diagnostic boundary. It asks whether the same concurrency behavior appears when terrain traversal, residency policy, scheduling, and `MeshInstance3D` ownership are removed while the real Godot Web runtime and real baked `TerrainChunkAsset` resources remain.

This is diagnosis, not an alternative runtime loading architecture.

## Why browser-headless

A native headless experiment cannot preserve the Web-specific layers implicated by the measurements. A rendered browser experiment preserves those layers but also mixes resource loading with traversal, residency, scene integration, and GPU work.

The browser-headless microbenchmark is the middle control:

```text
real threaded Godot Web export
        ↓
Web virtual filesystem / pack access
        ↓
ResourceLoader threaded request + polling
        ↓
TerrainChunkAsset deserialization
```

It intentionally omits:

```text
ChunkStreamer residency policy
nearest-first scheduling
hysteresis
MeshInstance3D creation
terrain traversal
representative GPU rendering
```

If the Web concurrency pattern remains in this reduced experiment, the evidence points below `ChunkStreamer`. If it disappears, the interaction with the production streaming lifecycle remains material and must be isolated further.

## Experiment implementation

The experiment scene is:

```text
res://demo/experiments/WebResourceLoadingExperiment.tscn
```

It loads the deterministic production streaming fixture manifest generated by `StreamingDemoFixtureBaker` and selects a stable coordinate-ordered sample of 24 LOD-0 chunk asset paths.

For each concurrency value:

```text
1, 2, 4, 8
```

it performs three repetitions. Each repetition requests the same real asset sample with `ResourceLoader.load_threaded_request()`, polls completion once per Godot process frame, retrieves each completed resource with `ResourceLoader.load_threaded_get()`, and records:

- total batch duration;
- assets per second;
- average request latency;
- maximum request latency;
- peak active requests;
- per-asset observed latency;
- failure state.

The experiment does not instantiate meshes and does not call `ChunkStreamer`.

## Automation

CI exports the scene with the existing `Web Threads` preset, preserving the same Godot threaded-Web runtime used by the streaming Integration Preview. A local HTTP server supplies the cross-origin-isolation headers required for browser threads, and headless Chromium executes the export.

The raw JSON evidence is uploaded as a CI artifact. Timing values are evidence, not CI thresholds. CI fails only when the experiment cannot execute coherently, a resource fails to load, the threaded Web runtime cannot run, or no result is emitted.

This keeps correctness deterministic without pretending shared-runner timing is deterministic.

## Cache provenance

The browser process is fresh for the automated experiment, and the local HTTP server sends `Cache-Control: no-store`. This reduces HTTP response-cache reuse but does not establish a laboratory-cold operating-system, browser-internal, Godot, or Web virtual-filesystem cache.

The output therefore records cache provenance explicitly rather than labeling the run simply `cold`.

## Rendering limitation

Headless Chromium still runs the real Godot Web export, but it is not a representative rendering benchmark. The experiment is deliberately concerned with resource acquisition/deserialization. It must not be used to infer GPU cost, compositor cost, or rendered mobile frame time.

The rendered mobile matrix remains the end-to-end validation surface for those interactions.

## Interpretation rule

Compare the browser-headless result against both existing controls:

1. native headless resource-loading matrix;
2. rendered mobile-Web streaming matrix.

The important signals are throughput scaling and request-latency scaling as concurrency rises.

A result where batch throughput stays flat while individual request latency grows roughly with concurrency would support the inference that the effective bottleneck is below `ChunkStreamer`, within or beneath the Web resource-loading path measured here.

A result where browser-headless throughput scales normally would reject that simple explanation and make the production streaming interaction, browser/device differences, or rendering environment material to the next diagnostic step.

Do not change production loading architecture from this experiment alone. Record the measured result in the current resource-loading performance report, compare it with the existing evidence, and make the loading-architecture decision from the combined evidence.
