Engine at a glance

The engine separates sampled scalar-field generation and meshing from runtime terrain residency. Terrain is generated and baked offline; runtime systems consume precomputed chunk assets.

Using the engine

Create and mesh a point field

PointFieldResource represents a regular sampled scalar field. Cell dimensions describe cells; the sample lattice is one sample larger on every axis. Density values above the iso-level are solid and values below it are empty.

var field := PointFieldResource.new()
field.cell_dimensions = Vector3i(16, 16, 16)
field.sample_spacing = 1.0
field.noise = FastNoiseLite.new()
field.regenerate()

if field.is_data_current():
    var mesh := SurfaceNetsMesher.new().generate_mesh(field, 0.0)

Surface Nets accepts only current field data. Configuration changes deliberately leave previous packed data available but mark it stale, so consumers must not treat retained stale channels as authoritative meshing input.

Stream precomputed chunks

Runtime streaming starts from a baked TerrainChunkManifest. ChunkStreamer owns asynchronous loading and residency, not terrain generation.

var streamer := ChunkStreamer.new()
streamer.manifest = preload("res://path/to/terrain_manifest.tres")
streamer.load_radius = 2
streamer.unload_radius = 3
streamer.max_load_starts_per_frame = 2
streamer.max_concurrent_loads = 4
add_child(streamer)

streamer.load_chunk(Vector3i.ZERO)
# Or drive automatic residency:
streamer.update_residency(player_position)

load_chunk() is asynchronous and idempotent. Observe completion through is_chunk_loaded(), get_chunk_load_state(), or the chunk_loaded signal. Automatic residency admits chunks inside load_radius and retains active chunks until they leave unload_radius.

Important Surface Nets boundary

Surface Nets needs neighboring cell context to emit topology around crossed sample edges. Chunk or region generation must therefore provide suitable overlap or halo data when surfaces reach field boundaries. The mesher intentionally does not reach into neighboring chunks itself.

Subsystem ownership

PointFieldResource

Authoritative scalar-field representation. Owns sample geometry, densities, indexing, sampling, validation, serialization, and generation-time field logic.

SurfaceNetsMesher

Consumes a current point field and produces an indexed ArrayMesh. It does not own field generation or runtime streaming.

ChunkAssetBaker

Owns offline chunk asset creation and persistence.

TerrainChunkManifest

Catalogs precomputed chunk assets and their spatial metadata.

ChunkStreamer

Owns runtime residency, threaded loading execution, nearest-first scheduling, loading budgets, hysteresis, metrics, and resident scene instances. It does not invoke procedural terrain generation.

Architectural rule: preserve subsystem contracts before optimizing. Performance work should remain behind stable interfaces unless measured evidence justifies a deliberate contract change.

Common library boundary

The repository defines a separate common-library layer for proven Godot capabilities whose ownership extends beyond voxel terrain. Dependency direction is project / demos → voxel terrain engine → common library; dependencies must not point upward. Promotion is an architectural decision based on genuine project-independent responsibility, not a generic shared, utils, or folder-cleanup mechanism. Scalar fields, terrain meshers, chunk assets, manifests, and streaming remain voxel-engine concerns.

NoClipCameraController is the first promoted common capability. It lives under common/input/, while demos and mobile-control validation consume that authoritative implementation. The promotion includes independent common-component validation so reuse does not turn the voxel engine into the owner of a project-general camera controller.

How the project develops

  1. Feature branches: work is performed on branches named for the feature, never generic change branches.
  2. Architecture first: substantial work identifies ownership, contracts, edge cases, and validation before production changes.
  3. Automated proof: deterministic headless tests validate observable behavior and architecture guards.
  4. Human-visible proof: substantial engine features have validation scenes using real public APIs and runtime paths.
  5. Browser proof: relevant validation is exposed through the long-lived GitHub Pages Integration Preview.
  6. Decision records: durable architecture belongs in ADRs; measured evidence in performance records; roadmap changes preserve their history.

The project treats feature delivery as a chain: production behavior → automated proof → human-visible proof → published browser proof.

Engineering-memory distillation

The continuity branch is evaluating a formal distillation protocol rather than treating chat summaries as automatically authoritative memory. The current experimental record kinds are observation, decision, assumption, uncertainty, and claim. Derivation is represented only by a non-empty premise graph; conclusion and epistemic_role are not part of the current protocol.

Normative standing is not stored as proposition authority. When authority matters, it is resolved from external provenance source metadata and may propagate through premise chains. Current authority-bearing source types are owner_instruction and governed_artifact; repository files, commits, tests, workflow runs, summaries, and chats do not acquire normative authority merely by existing.

External grounding uses typed provenance roles: primary, corroborating, and context. General graph relations are limited to supports, contradicts, depends_on, and supersedes. Structural validation and canonical admission are deliberately separate.

The Steward authorized a bounded successor-contract drafting tranche for pems/2. The technical draft is complete but noncanonical. It may not advance into migration-governance review while canonical v1 authority is ambiguous.

Reusable component promotion

Components move into the common library only when their existing responsibility is independently useful outside voxel terrain, their API is understandable without terrain knowledge, and their validation can stand alone. Extraction must preserve or clarify the public contract, update consumers to use the authoritative library version, and avoid broadening responsibilities merely to make code appear generic. If substantial redesign is required, that redesign is separate architectural work.

Current roadmap

The current milestone on main is resource-loading analysis. Large single-LOD validation identified precomputed resource-loading throughput as the first material scaling pressure visible in current instrumentation. The goal is diagnosis before optimization.

The implementation investigation is currently represented by draft PR #53, Resource-loading analysis. It remains open and draft and is not described here as shipped behavior.
